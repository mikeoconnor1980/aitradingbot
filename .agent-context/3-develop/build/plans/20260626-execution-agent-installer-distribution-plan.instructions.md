# Task Checklist: Execution Agent Installer Distribution

## Overview

Complete the existing Azure Blob Storage plus API-proxy distribution flow for the `TradePilot.ExecutionAgent` Windows installer so the UI can reliably show available installer downloads and the worker can safely consume update metadata.

The high-level architecture is sound: keep installer blobs private, let CI publish versioned release artifacts to Blob Storage, and let the API provide authenticated metadata and download routes to the browser and agent. The main gaps are operational: the GitHub workflow uploads `artifacts/installer` but does not build it, release metadata is static in appsettings, hashes are not propagated, and the controller-level anonymous access model is too broad for a subscription product.

## PBI Details

The current UI shows `No installer files available on the server yet.` The repo already has most of the distribution plumbing:

- `deploy/worker/build-installer.ps1` packages the worker as a self-contained `win-x64` service, ZIP, Inno Setup EXE, and SHA256 file.
- `infrastructure/modules/storage-account.bicep` provisions a private `installers` blob container.
- `src/TradePilot.Infrastructure/Storage/BlobInstallerStore.cs` and `LocalInstallerStore.cs` implement the installer store abstraction.
- `src/TradePilot.Api/Controllers/AgentController.cs` exposes installer info, download, and heartbeat update metadata.
- `.github/workflows/deploy.yml` has an `upload-installers` job using Azure OIDC and `az storage blob upload --auth-mode login`.

The likely immediate reason the UI is empty is that the CI upload job never builds the installer and only uploads from a directory that is not created in that job. Even when blobs exist, the API derives expected filenames from static `AgentUpdate` configuration instead of reading a release manifest from storage, so version/hash drift can still produce false empty or unsafe update states.

### Current State and Gaps

- Blob Storage plus API download is already partially implemented and is the right direction.
- `upload-installers` depends on `build-and-test` but does not run the Windows installer build.
- `AgentUpdate:LatestVersion` and `AgentUpdate:Sha256Hash` are static config values; hash is empty by default.
- `.sha256` files are generated locally but not used as the API's authoritative metadata source.
- Download URLs are relative, which is brittle for worker auto-update.
- `AgentController` has class-level `[AllowAnonymous]`, so browser download endpoints are public unless the controller is refactored.
- Storage access uses an account-key connection string in the API; managed identity should replace that after Key Vault/storage hardening.

### Decision

Use Azure Blob Storage as the private artifact store and the API as the distribution boundary.

Add a blob-backed `latest.json` release manifest as the source of truth for installer metadata. CI should build the installer, compute hashes, upload versioned artifacts, upload the manifest, and then the API should serve metadata/downloads from that manifest rather than static appsettings.

### Acceptance Criteria

- GitHub Actions builds the execution-agent installer on `windows-latest` for main-branch releases.
- CI uploads versioned EXE, ZIP, SHA256, and `latest.json` artifacts to the private `installers` blob container.
- `GET /api/agent/installer/info` returns accurate availability, version, size, filename, and SHA256 values based on Blob Storage metadata.
- The Profile UI shows download buttons when blobs exist and clearer empty states when metadata or blobs are missing.
- `GET /api/agent/installer/download?format=exe|zip` streams the correct file without loading it fully into memory.
- Worker update metadata includes an absolute or resolvable download URL and non-empty SHA256 hash.
- Browser download endpoints require authenticated/subscribed users, while agent heartbeat remains compatible with the existing agent check-in flow.
- Storage remains private with no public blob access.

## Objectives

- Make the installer available from the site without committing binary release artifacts by hand.
- Make release metadata deterministic and generated by CI.
- Preserve a private artifact store and avoid public blob URLs by default.
- Provide integrity verification through SHA256 hashes.
- Lay groundwork for controlled agent update rollout and rollback.

### Scoping Notes

- The current Blob Storage plus API approach is sensible and should be completed, not replaced.
- The fastest fix for the visible UI issue is the CI build/upload change, but the release manifest should follow immediately to avoid stale version/hash drift.
- Streaming through the API is acceptable at current expected scale. Direct short-lived SAS downloads can be considered later if API egress or request duration becomes a problem.
- Download authentication needs care because the same controller currently serves both browser and agent workflows.

## Dependencies

- .NET 10 SDK on GitHub Actions Windows runners.
- Inno Setup availability or successful scripted install during the packaging job.
- Azure OIDC deployment principal with `Storage Blob Data Contributor` on the installer storage account/container.
- Existing installer storage account from Bicep.

## Success Criteria

- A main-branch workflow run builds the installer and uploads versioned artifacts plus `latest.json`.
- Blob Storage contains the expected EXE, ZIP, SHA256, and manifest files for the current release.
- `/api/agent/installer/info` reports available installer files instead of the empty state.
- Profile page displays download buttons for available formats.
- Download endpoint streams the expected binary and preserves content type/filename.
- Worker update metadata has a valid URL and non-empty hash.
- Hash verification succeeds for a published installer and fails for a tampered file.
- Browser installer downloads are protected by authentication/subscription policy or an explicitly documented temporary exception.
