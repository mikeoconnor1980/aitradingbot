## Summary

Wire signal-mode strategies into the shared scheduler/backtest pipeline so RSI entry conditions are evaluated with a populated indicator context and can produce executable trade signals. Separate signal-mode execution from the grid-only `DeployGrid` flow so signal strategies can actually open and manage positions.

### User Story

> As a **trader**, I want **signal-mode strategies to evaluate and execute through the live and backtest engine** so that **an RSI strategy that passes its conditions can actually open trades instead of remaining UI-only configuration**.

### Business Value

This closes the gap between the new signal-mode strategy builder and the backend trading engine. Without it, users can save and preview RSI strategies but they never trigger trades because the runtime pipeline does not populate indicator context and still routes execution through the grid-only controller.

---

## Problem Statement

The current signal-mode implementation is incomplete across the execution pipeline:

1. **Indicator requirements are never wired into runtime context building** — `IndicatorExtractor` exists, but `StrategyScheduler` calls the `IMarketContextBuilder.Build(...)` overload that does not pass required indicators.
2. **Signal evaluation sees no indicator context** — `ConditionEvaluator` returns `SetupDetected = false` with `"Indicator context not available."` when signal conditions are evaluated without populated indicator requirements.
3. **Execution remains grid-only** — after signal-mode evaluation, the pipeline still routes to `GridController`, which assumes grid config exists and emits `DeployGrid` signals.
4. **Backtest/live parity is broken for signal strategies** — the shared pipeline exists, but only grid behavior is executable end-to-end.
5. **The UI now exposes a capability the engine does not actually support** — RSI strategies can be created, saved, and previewed, but they do not produce trades.

---

## Requirements

### Functional Requirements

1. `StrategyScheduler` must derive required indicators from the strategy config before building `MarketContext`
2. `StrategyScheduler` must call the market-context builder overload that accepts required indicator requirements
3. `MarketContext` for signal strategies must populate `IndicatorContext` for all enabled entry conditions required by the current strategy
4. Signal-mode strategies must evaluate successfully when sufficient candle history exists for the requested indicators
5. Signal-mode execution must no longer rely on grid deployment behavior or require `GridConfig`
6. Introduce a signal-specific post-evaluation execution path that can emit executable trade intents for position entry/exit
7. Backtesting must support signal-mode strategies opening trades through the shared runtime pipeline
8. Runtime scheduling must support signal-mode strategies through the same candle-close flow used by backtests
9. Exit rules and risk rules must apply consistently after a signal-based position is opened
10. Signal evaluation reasons must be visible in backtest/debug output so a user can tell why a signal strategy did or did not trigger

### Non-Functional Requirements

- Grid-mode behavior must remain unchanged with no regression to `DeployGrid`, take-profit, or stop-loss workflows
- Signal-mode orchestration must remain deterministic and candle-close-driven, consistent with the scheduling architecture
- The runtime branch between grid mode and signal mode must be explicit and easy to extend for future EMA/MACD conditions
- The implementation must preserve backtest/live parity by using the same shared strategy evaluation path in both environments

## Acceptance Criteria

- [ ] **Given** a signal strategy with one RSI condition, **When** `StrategyScheduler` builds `MarketContext`, **Then** it passes extracted indicator requirements into the market-context builder
- [ ] **Given** a signal strategy requiring RSI(14), **When** sufficient candle history exists, **Then** `IndicatorContext` contains RSI(14) values for the evaluator
- [ ] **Given** a signal strategy with valid indicator context, **When** the condition passes, **Then** strategy evaluation returns `SetupDetected = true`
- [ ] **Given** a signal strategy with valid indicator context, **When** the condition fails, **Then** strategy evaluation returns `SetupDetected = false` with a meaningful reason
- [ ] **Given** a passing signal strategy, **When** the execution pipeline processes the approved signal, **Then** it emits and executes a signal-mode trade intent rather than `DeployGrid`
- [ ] **Given** a signal strategy, **When** the runtime pipeline executes it, **Then** no grid configuration is required to open a position
- [ ] **Given** a signal strategy backtest where RSI conditions are met, **When** the backtest completes, **Then** at least one trade is recorded
- [ ] **Given** a signal strategy backtest where RSI conditions are not met, **When** the backtest completes, **Then** no trades are recorded and the debug output explains why
- [ ] **Given** an existing grid strategy, **When** backtests and scheduler flows are run after this change, **Then** the existing grid execution behavior remains unchanged
- [ ] **Given** signal-mode evaluation debug output, **When** a condition fails because data is missing or thresholds are not met, **Then** the recorded reason is available to developers and users

### Design Notes

**Indicator Requirements Must Be Pulled from Strategy Config**
`IndicatorExtractor.Extract(config)` already exists and should become the single source of truth for which indicators the runtime must compute for a strategy.

**Signal Execution Must Branch Before Grid Logic**
Signal-mode strategies should not be forced through `GridController`, because grid lifecycle state and `DeployGrid` semantics are not valid for direct signal-entry strategies.

**Backtest and Live Must Share the Same Orchestration Rule**
The fix belongs in the shared scheduler/execution path, not in a backtest-only special case. Otherwise signal-mode parity will diverge again.
