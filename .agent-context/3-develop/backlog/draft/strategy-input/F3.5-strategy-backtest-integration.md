# F3.5 — Strategy–Backtest Integration

---

## Summary

Connect saved strategies to the backtesting system so that all backtests run against a persisted strategy. Replace the current manual-entry backtest form with a strategy-picker workflow where the user selects a saved strategy (read-only), configures only backtest-specific parameters (date range, capital, fees), and runs the backtest. Link every `BacktestRun` to its source `Strategy` and `StrategyRevision`. Provide a strategy-scoped backtest history view so users can compare performance across revisions.

### User Story

> As a **trader**, I want to **select a saved strategy and backtest it directly** so that **I can validate my strategy against historical data and track how parameter changes affect performance across revisions**.

### Business Value

Without this, the strategy builder and backtester are disconnected tools — users configure strategies in one place and manually re-enter the same parameters in another. This PBI closes the loop: build → save → backtest → compare → refine. It also creates the data linkage needed to answer "which version of my strategy performed best?" — a core value proposition for the platform.

---

## Problem Statement

The current backtest form (`backtest-form.component.ts`) builds a `BacktestStrategyConfig` from ~15 individual form fields entered manually every time. There is no way to load a saved strategy. After F2 ships, users will have persisted strategies with canonical JSON, but the backtester cannot consume them. Additionally, `BacktestRun` has no foreign key to `Strategy` or `StrategyRevision`, so backtest results cannot be traced back to the strategy that produced them. This makes it impossible to answer "how did my strategy perform before vs after I changed the grid spacing?"

## Requirements

### Functional Requirements

#### Backtest Form Refactor — Strategy-First Workflow

- [ ] Remove all manual strategy parameter fields from the backtest form (grid levels, spacing, TP/SL, position size, leverage, etc.)
- [ ] Add a **strategy picker** (autocomplete/dropdown) that loads saved strategies from `GET /api/strategies`
- [ ] When a strategy is selected, display its configuration as a **read-only preview** (strategy name, mode, grid params, exit rules, risk settings). The strategy is the source of truth — not editable in the backtest context
- [ ] Retain only backtest-specific fields as editable: date range, initial capital, maker fee, taker fee, slippage
- [ ] Intervals are derived from the strategy's timeframe configuration (not manually selected)
- [ ] Symbol is derived from the strategy's market field (not manually selected)
- [ ] The "Run Backtest" action submits the strategy's canonical JSON (from the persisted `StrategyConfig`) along with backtest-specific params
- [ ] Support deep-linking: `/backtesting?strategyId={id}` pre-selects the strategy in the picker

#### Navigation: Strategy → Backtest

- [ ] Add a **"Backtest"** action button to the strategy list page (`/strategies`) — per-row action alongside Edit and Delete
- [ ] Add a **"Backtest this strategy"** button to the strategy builder page (when viewing/editing a saved strategy)
- [ ] Both navigate to `/backtesting?strategyId={id}`, pre-selecting the strategy

#### Navigation: Backtest → Strategy

- [ ] Backtest results list (`backtest-list.component`) displays the **strategy name** column
- [ ] Backtest result detail (`backtest-result.component`) displays strategy name + revision number with a link back to the strategy (`/strategies/{id}/edit`)
- [ ] Clicking the strategy name navigates to the strategy detail/edit page

#### BacktestRun Entity — Strategy Linkage

- [ ] Add optional `StrategyId` (Guid?) to `BacktestRun` entity — references the `Strategy` used
- [ ] Add optional `StrategyRevisionId` (int?) to `BacktestRun` entity — references the specific `StrategyRevision` (from F3) that was active at the time of the backtest
- [ ] `BacktestRun.CreateQueued` accepts optional `strategyId` and `strategyRevisionId`
- [ ] Database migration adds nullable `StrategyId` and `StrategyRevisionId` columns to `BacktestRuns` table
- [ ] `RunBacktestRequest` includes optional `strategyId` field; the API resolves the current revision at submission time
- [ ] `BacktestRunResponse` and `BacktestRunSummary` include `strategyId`, `strategyRevisionId`, and `strategyName`

#### Strategy-Scoped Backtest History

- [ ] `GET /api/strategies/{id}/backtests` — returns all backtest runs linked to a strategy, ordered by creation date descending
- [ ] Response includes revision number for each run so the user can see which version was tested
- [ ] Frontend: strategy detail/edit page includes a **"Backtest History"** tab or panel showing all backtests for that strategy
- [ ] Group or filter by revision number — user can compare performance across versions
- [ ] Each row links to the full backtest result detail

#### Re-run from Results

- [ ] Existing "Re-run" action on backtest results now navigates to `/backtesting?strategyId={id}` with the same backtest-specific params (date range, capital, fees) pre-filled
- [ ] If the linked strategy has been deleted or is inactive, show a warning and fall back to displaying the config from `StrategyConfigJson` as read-only (no strategy picker selection)

### Non-Functional Requirements

- [ ] Strategy picker loads strategies efficiently (paginated or cached for reasonable list sizes)
- [ ] Deep-link navigation (`?strategyId=`) handles invalid/missing strategy IDs gracefully (toast notification + empty picker)
- [ ] Read-only strategy preview does not allow any mutation — defense in depth, not just disabled fields

## Acceptance Criteria

- [ ] **Given** I am on the backtest page, **When** I open the strategy picker, **Then** I see my saved strategies listed by name
- [ ] **Given** I select a saved strategy, **When** the form updates, **Then** strategy parameters display as read-only and only date range, capital, and fees are editable
- [ ] **Given** I am on the strategy list page, **When** I click "Backtest" on a strategy row, **Then** I am navigated to the backtest page with that strategy pre-selected
- [ ] **Given** I am editing a strategy in the builder, **When** I click "Backtest this strategy", **Then** I am navigated to the backtest page with that strategy pre-selected
- [ ] **Given** I run a backtest, **When** the run completes, **Then** the `BacktestRun` record includes the `StrategyId` and `StrategyRevisionId`
- [ ] **Given** I view a backtest result, **When** I see the strategy name, **Then** clicking it navigates to the strategy edit page
- [ ] **Given** I am on a strategy's detail page, **When** I view the backtest history panel, **Then** I see all backtests grouped by revision with key metrics
- [ ] **Given** a strategy has been deleted, **When** I view a backtest that referenced it, **Then** the strategy name shows with a "deleted" indicator and the link is disabled
- [ ] **Given** I navigate to `/backtesting?strategyId=invalid-guid`, **When** the page loads, **Then** I see a notification that the strategy was not found and the picker is empty

## Technical Considerations

### API Endpoints

| Method | Path | Description |
|--------|------|-------------|
| `GET` | `/api/strategies` | Existing (F2) — used by strategy picker |
| `GET` | `/api/strategies/{id}/backtests` | New — backtest history for a strategy |
| `POST` | `/api/backtests` | Existing — updated to accept optional `strategyId` |

### Database Changes

| Column | Table | Type | Nullable | Description |
|--------|-------|------|----------|-------------|
| `StrategyId` | `BacktestRuns` | `Guid` | Yes | FK to `Strategies` table |
| `StrategyRevisionId` | `BacktestRuns` | `int` | Yes | FK to `StrategyRevisions` table (F3) |

### Integration Events

None — this is a UI/API integration, not an event-driven feature.

### Jobs

None.

## Out of Scope

- **Batch backtesting** (running one backtest across multiple strategies simultaneously)
- **Auto-backtest on save** (automatically running a backtest when a strategy is saved/updated)
- **Strategy parameter overrides in the backtest form** (editable copy mode — explicitly excluded per design decision)
- **Backtest scheduling** (recurring backtests on a cron)
- **Performance regression alerts** (notifying when a new revision performs worse than the previous)
